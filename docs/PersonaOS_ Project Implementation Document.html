PersonaOS: Project Implementation Document

One Identity. One Memory. Infinite Intelligence.

Version 1.0 · 30 Sep 2026 · Built from the PersonaOS Abstract, Build Spec, Budget Estimate and design guide, extended with Gmail, Google Calendar and Google Drive integration.

1. Project overview

1.1 Purpose

PersonaOS is a personalized AI life-management assistant, not a plain chatbot. It remembers each user over time, knows their documents, tracks goals and tasks, and acts on their behalf (planning, scheduling, summarizing, emailing) through agentic tool use.

1.2 Objectives

  1. Give each user a persistent, private memory of their preferences and goals.
  2. Let users upload or connect documents and query them with RAG.
  3. Track goals, tasks and progress, and show productivity analytics.
  4. Act through tools: study plans, calendar events, Drive imports, Gmail search and drafts.
  5. Manage memory responsibly: lifecycle (forgetting, supersession), user visibility and deletion.
  6. Deploy as a secure, cloud-hosted web application.

1.3 Alignment

SDG 3 (Well-being), SDG 4 (Quality Education), SDG 8 (Decent Work and Economic Growth): lifelong learning, productivity and personalized assistance.

1.4 Scope

2.2 Responsibility split (do not blur)

2.4 Agent design (LangGraph)

START → load_context → agent ⇄ tools → save_memory → END
  • load_context: recall memories (recall(user_id, message)), load last N chat messages.
  • agent: LLM call with system prompt, memories, history and tools bound. Tool calls go to tools; otherwise to save_memory.
  • tools: execute tool calls, return to agent. Hard cap: 5 iterations per turn.
  • save_memory: save_turn to Mem0, update memory_meta, persist chat messages.

Tool rules: user_id always comes from the verified token in agent state, never from LLM arguments. Text retrieved from documents or emails is data, not instructions (prompt-injection defence).

2.5 Google integration design

User clicks "Connect Google" (Streamlit)
  → GET /integrations/google/start?scopes=calendar,drive,gmail
  → redirect to Google consent (access_type=offline, state=signed nonce)
  → Google redirects to /integrations/google/callback?code=...
  → backend exchanges code, encrypts refresh token (Fernet), stores in google_tokens
  → tools load token per user_id, refresh access token, call the API

Rules:

  • Firebase login identifies the user; Google OAuth is a separate consent granting data access.
  • Request incremental scopes (Calendar first, then Drive, then Gmail) so users grant only what they use.
  • Imported Drive files and emails go through the normal ingestion pipeline (chunk, embed, Chroma with user_id), so RAG and Mem0 need no special path.
  • Fetch the minimum: a specific file or the last N emails, never a whole mailbox.
  • Disconnect revokes the token at Google, deletes the stored token, and optionally purges imported chunks.
Capability Scope Google tier
Calendar read/create calendar.events Sensitive
Drive (picked or app-created files) drive.file Non-sensitive
Drive (read all) drive.readonly Restricted
Gmail read/search gmail.readonly Restricted
Gmail send / drafts gmail.send, gmail.compose Sensitive

Deployment mode: Testing publishing status (up to 100 test users, "unverified app" warning, 7-day refresh-token expiry for restricted scopes). Public launch path is in Section 12.

7. Memory lifecycle specification

Write: mem0.add(messages, user_id); upsert memory_meta(state=active, strength=1.0, access_count=0).

Read: mem0.search(query, user_id, limit=k*3) → join memory_meta → drop archived/superseded → score = relevance × strength → top k → reinforce (access_count += 1, last_accessed_at = now, strength = min(1, strength + 0.1)).

Decay (nightly): strength = exp(-days_since_last_access / S), S = base_days × (1 + 0.5 × access_count), base_days ≈ 14. < 0.5 → stale; < 0.15 → archived (kept, but excluded from recall).

Supersession: on Mem0 update/contradiction (or LLM conflict check), old row → superseded, superseded_by = new id.

Tests: fake clock; 60 simulated idle days moves a memory to stale/archived; contradiction supersedes.

10. Security and privacy checklist

  • Every query filters by user_id (SQL, Chroma metadata, Mem0)
  • Tool user_id comes from the verified token, never LLM output
  • Upload allowlist, size limit, safe parsing, no execution of content
  • Retrieved document/email text treated as data, not instructions
  • Secrets in env vars; Google refresh tokens encrypted (Fernet key in env)
  • OAuth state parameter validated; redirect URIs exact
  • Minimum Google scopes; incremental consent
  • Email content not persisted unless the user saves it
  • Email send and calendar writes confirmed by the user
  • HTTPS, CORS locked, rate limits on /chat and uploads
  • User can view/delete memories, disconnect Google, delete all data
  • Test Google account with fake content used for development; no real personal data through free-tier LLMs
